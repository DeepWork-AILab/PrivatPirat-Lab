# PP-LAB Builder predeploy lessons — 2026-08-30

**Status:** `FIELD NOTE / DRAFT MATERIAL`

## Ситуация и реальная цель

Нужно было довести `PrivatPirat Reproducible Node Builder v0.1` до состояния, когда владелец вводит данные нового VPS, а Builder сам строит и проверяет три уже принятых маршрута I/II/III.

К концу работы deployment engine уже существовал. Главная задача была не «ещё раз спроектировать VPN», а сделать первый clean-room run безопасным и воспроизводимым со смартфона через Termux.

## Что оказалось ценным

### 1. Capability важнее предполагаемой роли

Первоначальная чистая граница Builder ожидала прямой root SSH. Реальный провайдер выдал обычный SSH account. Вместо ручной серверной правки был выполнен различающий read-only тест: прямой UID не root, но `sudo -n` даёт effective UID 0.

Правильное решение оказалось не в подмене username и не в передаче sudo-пароля, а в capability-based transport:

- direct root работает как прежде;
- non-root принимается только после доказанного passwordless sudo;
- пароль sudo не входит в архитектуру Builder.

Переносимый вывод: автоматизация должна проверять нужную способность системы, а не угадывать её по имени пользователя или типичному образу VPS.

### 2. Safety-check способен сам создавать false positive

Один защитный scanner искал запрещённые конструкции по всему diff. Он нашёл строки с названиями опасных инструментов внутри unit tests, которые как раз проверяли отсутствие этих инструментов в production source.

STOP сработал безопасно, но классификация была неверной.

Правильное решение:

- executable source проверяется отдельно;
- negative fixtures не смешиваются с runtime scan;
- критические route functions защищаются структурным/byte-identical invariant, а не только grep-паттернами.

Переносимый вывод: safety tooling тоже требует модели ложноположительных срабатываний и собственных acceptance criteria.

### 3. Обычный Linux path может быть не переносимым

Новые тесты использовали `/tmp/x`. На Termux это привело к `PermissionError` ещё до проверки самой sudo-логики.

Исправление — `tempfile.TemporaryDirectory()`.

Переносимый вывод: если продукт заявлен smartphone-first, Termux является production-like target для тестов, а не экзотическим исключением.

### 4. Generated noise нельзя путать с source dirt

Python verification создал `__pycache__`. Следующий wrapper принял эти generated directories за неожиданное изменение рабочего дерева и остановился.

Правильное решение:

- generated bytecode/cache игнорируется;
- deployment gate отдельно проверяет tracked worktree и staged index;
- source-integrity check не должен зависеть от побочных файлов обычного test run.

### 5. Секретный transport важнее удобного SCP

После появления sudo-mode обычный `scp` в root-owned path перестал быть корректной моделью. Можно было бы временно складывать материал в `$HOME` обычного пользователя и затем перемещать его через sudo, но это увеличивало след приватных данных.

Принято другое решение: payload передаётся через system OpenSSH stdin/stdout прямо privileged shell/cat path; локальные private files остаются с restrictive permissions; password-like secrets не появляются в argv.

Переносимый вывод: privilege escalation и secret transport нужно проектировать вместе.

## Где процесс стал хуже, чем должен был быть

После полезных CODE-4/CODE-5 исправлений началась цепочка wrapper-команд, tmux-сессий, ручного поиска fingerprint, generated cache и повторных локальных STOP.

С точки зрения безопасности результат хороший: clean-room VPS не был случайно изменён. С точки зрения operator experience — плохой: человек потратил много внимания на механическое обслуживание automation harness вместо основного действия.

Это особенно важно, потому что `AGENTS.md` уже формулировал правильные принципы:

- не превращать человека в канал передачи между системами;
- smoke-test критическое звено до длинной цепочки;
- повторяемую ручную операцию автоматизировать;
- при unexpected result делать один различающий read-only test.

Фактический урок: текстовое governance правило слабее, чем правило, встроенное в интерфейс, Builder и tests.

## Что изменилось в методе

`DECISION` — следующий clean-room run не должен обрастать новыми helper layers без реального blocker.

`DECISION` — локальные operational inputs должны потребляться локально; чат не должен становиться clipboard для trust anchors или серверных данных.

`DECISION` — следующий blocker сначала доказывается одним read-only distinguishing test; только после этого разрешается CODE change.

`DECISION` — operator burden считается частью acceptance, а не вторичной косметикой.
