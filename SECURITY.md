# Security Policy

## Область

PrivatPirat Lab — публичная документация экспериментального сетевого контура. Репозиторий не является хранилищем рабочих конфигураций, credentials, inventory или клиентских профилей.

## Никогда не публиковать

- пароли, recovery codes, API tokens и private SSH keys;
- фактический адрес/hostname `PP-LAB-01` без отдельного решения владельца;
- UUID, REALITY private key, Short ID, target/SNI;
- пароль Hysteria2 и private key TLS-сертификата;
- рабочие URI подключения и subscription URL;
- полный клиентский или серверный конфиг;
- сырые выводы `journalctl`, inventory, firewall dump или process environment;
- backup-файлы и историю shell, способные раскрыть перечисленное.

Даже публичные части конфигурации перед публикацией должны быть санитизированы: совокупность адреса, порта, домена, SNI, fingerprint и времени теста может стать чувствительным идентификатором.

Этот раздел регулирует публикацию. В текущем приватном операторском чате точные IP/SSH metadata и REALITY target/SNI могут использоваться после явного разрешения владельца для конкретного run; это не разрешает перенос значения в публичный репозиторий, issue, PR или evidence. Пароли, private keys, UUID, Short ID, Hysteria credentials и рабочие URI такой оговоркой не раскрываются.

## Evidence

Публичное evidence должно содержать только минимально необходимое:

- дату и обобщённый тип сети (`Wi‑Fi` или `mobile`);
- route ID и версии ПО;
- описание метода теста;
- булев результат совпадения exit IP без самого IP;
- HTTP/HTTPS, DNS, repeatability, restart и regression verdict;
- санитизированную ошибку, если тест завершился FAIL.

Сырые логи и конфиги хранятся вне репозитория с ограниченным доступом.

## Если секрет обнаружен

1. Остановить работу и не распространять ссылку на утечку.
2. Считать секрет скомпрометированным и отозвать/заменить его.
3. Проверить связанные credentials и журналы доступа.
4. Удаление из Git history выполнять только по отдельному согласованному плану.
5. Зафиксировать санитизированный факт инцидента без повторной публикации секрета.

Не открывайте публичный issue с уязвимостью или секретом. Используйте private vulnerability reporting GitHub, если оно включено для репозитория, либо согласованный внепубличный канал владельца.
